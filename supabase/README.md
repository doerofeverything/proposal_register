# Supabase setup

## 1. Tables and permissions

Run **install.sql** in your project's SQL Editor for the complete schema, permissions, transaction functions, options and all 152 historical records. Existing members and records are preserved.

Alternatively, run these scripts separately, in this order:

1. `setup.sql` creates `register_members`, `proposals`, and `register_settings`.
2. `cloud-storage.sql` adds `register_options` and membership-checked transactions for saving proposals, updating numbering, and importing backups.
3. `seed.sql` imports all 152 historical rows, including source metadata, and advances the current financial year's next sequence.

These scripts preserve existing proposal records. Re-running historical inserts skips existing keys. Review any pre-existing conflicting records before importing. Only explicitly approved members can access the shared register. `register_members` contains usernames and Supabase Auth user IDs, never passwords.

Run `npm run db:check` for a read-only connection check showing table availability and record counts. It needs the server secret in `.env`; it does not print credentials or proposal contents.

## 2. Server environment

Your `.env` needs:

```env
NEXT_PUBLIC_SUPABASE_URL=https://your-project.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=your-publishable-key
SUPABASE_SECRET_KEY=your-server-secret-key
```

The secret key is used only on the server for username lookup and by the account-creation script. A legacy service-role key is also accepted in `SUPABASE_SECRET_KEY`. Never put this key in a `NEXT_PUBLIC_` variable or send it to the browser. Email login needs only the URL and publishable key.

Restart `npm run dev` after editing environment variables. The app has no fallback username or password. Existing `flowdesk_session` cookies no longer grant access.

## 3. Create your login

Add these to your local `.env`, using an email you control if you need password recovery:

```env
SEED_USER_EMAIL=your-email@example.com
SEED_USER_USERNAME=your-username
SEED_USER_PASSWORD=
```

Run:

```sh
npm run seed:user
```

The script creates a confirmed Supabase Auth account and links it to `register_members`. Leaving the password blank generates a random password, shown once in the command output. Set `SEED_USER_PASSWORD` to a password of at least 12 characters if you want to choose one. Supabase applies its configured password policy. Existing accounts and passwords are never overwritten. Remove the `SEED_USER_*` values after creating the account.

Example resulting data:

| Location | Value |
| --- | --- |
| `auth.users.email` | Your configured email |
| `auth.users.encrypted_password` | Hash managed by Supabase Auth |
| `register_members.username` | Your configured username |
| `register_members.user_id` | The UUID generated by Supabase Auth |
| Login password | Generated password printed by the seed command |

You can sign in using the username **or** email with that password. Changing the display name in Auth metadata does not grant workspace access. Membership is checked in the database on login and protected-page requests.

Alternatively, create the user using **Authentication → Users → Add user**, then add the membership manually:

```sql
insert into public.register_members (user_id, username)
select id, 'YOUR_USERNAME_HERE' from auth.users
where lower(email) = lower('YOUR_EMAIL_HERE');
```

## 4. Proposal records and settings

The UI displays database records. There are no fictional proposals or default login accounts. The historical import contains the original 152 proposal records. To bring across additional browser records, import a previous JSON backup in Settings. Imports retain existing history and reject conflicting proposal numbers.

Treatment types and locations are loaded from `register_options`. Manage these lookup rows in Supabase; treatment labels must also satisfy the proposals table's treatment constraint. Financial year and next sequence are loaded from `register_settings` and can be changed through the UI.

Writes require `cloud-storage.sql`. Direct table writes by authenticated clients are revoked, so sequence allocation and revision creation cannot bypass the shared transaction lock. The app's database clients use the signed-in user's token; the server secret is used only for account setup and username lookup.
